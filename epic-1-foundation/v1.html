01Summary

HEAD operates as a small AI consulting firm. Today there is no shared system. Client information lives in Telegram chats, voice notes, scattered docs, and people's heads. A returning company sometimes has to re-explain their story because no one remembers the last conversation. The first thing the internal system needs is a place to put a client — a single shared record, accessible to the team, with the fields HEAD actually wants to capture, owned by a specific person, governed by a permission system the founders control.

This epic delivers that foundation. Anyone on the team can log in with email and password — no SSO, no 2FA, no email verification, nothing fancy. A hard-coded system admin account exists from day one so the founders never lock themselves out. Inside the app there is a sidebar, a search, a "+ New lead" button in the top bar, a Clients list, a Client detail page, and a Settings area. The data model treats lead and client as the same record with a status flag — a lead is just a client at an early status.

What makes this epic non-trivial is that everything is dynamic. Roles are not hard-coded — admins create roles and assign permissions to them. Fields on a client/lead are not hard-coded either — admins create the fields they want and decide for each field whether it appears on the new-lead form, on the client detail page, on both, or on neither. The only fields the system itself owns are the three it cannot function without: company name, owner, and status. The system seeds a default Admin role (everything) and a default Member role (basic read/create) so day one isn't a blank canvas, but both are editable. The status list ships blank — no seeded values. Admins define the team's vocabulary themselves before anyone can create a lead. Every change to clients, users, roles, permissions, fields, and workspace settings is recorded in an admin-visible audit log.

This epic deliberately ships the shell of the client detail page, not the engagement workspace or the artifacts feed. Those sit in EPIC-3 and EPIC-4. The page renders an empty engagements list and an empty artifacts feed in MVP — placeholders waiting for those epics to populate them.

02Problem

HEAD has roughly eight people across founders, engineers, sales, support, and contractors. The team coordinates client work through Telegram messages, voice memos, and ad-hoc documents. When a lead arrives, it lives in whichever conversation thread it appeared in. There is no shared list anyone can scan. There is no agreed structure for what to capture about a new lead, so what gets written down varies by who took the call. When a previously-engaged client returns six months later, whoever picks up the phone has to rely on personal memory or hunt through chat history to figure out what was done last time. There is no system of record.

Building a workflow tool on top of nothing would mean baking decisions HEAD has not yet made into code — what counts as a lead, what fields matter, who can do what. The founders have explicitly asked for a flexible foundation: dynamic fields, dynamic roles, dynamic permissions. The cost of guessing wrong is rework; the cost of being flexible from the start is one well-designed framework. This epic is the framework — the place where every other module plugs in its data and its rules.

03Goals & success metrics

04Personas

Team member

Anyone with an account

Founder, engineer, sales person, support person, or contractor with a HEAD account. Logs in to find clients, create leads, see who owns what. Permissions are governed by their role. May or may not be able to delete or manage settings — depends on the role assigned to them.

Admin

A team member with admin permissions

Typically a founder. Manages users, defines roles, decides which permission each role gets, defines the fields on a client/lead, decides where each field appears, defines the list of statuses, and reviews the audit log. An admin is created by being assigned the seeded Admin role (or any custom role that includes the manage_* permissions).

System admin

Hard-coded superuser

A built-in account, seeded at installation with credentials configured outside the database. Always has every permission, including ones not yet defined. Cannot be deleted, cannot be deactivated from the UI, cannot have its permissions reduced. Exists so the founders never get locked out of their own system if a custom role configuration goes wrong.

05In scope / Out of scope

In scope

  • Email + password authentication, no verification step, no 2FA, no OAuth, no magic links
  • Hard-coded system admin account seeded at installation
  • App shell: sidebar nav (Pipeline, Clients, Settings), top bar (search, "+ New lead", user menu)
  • Single shared workspace — one HEAD installation, one workspace inside it
  • Client / lead data model: same record, distinguished by a status field
  • Three system fields that cannot be deleted: company name, owner, status
  • Dynamic custom field engine — admin-defined fields of types: single-line text, long text, number, date, single-select, multi-select, checkbox, file upload
  • Per-field placement — admin chooses for each field whether it appears on the new-lead form, the client detail page, both, or neither
  • Dynamic role system — admins create roles, name them, and assign discrete permissions to them
  • Dynamic permission catalog — every mutating action in EPIC-1 is governed by a discrete permission
  • Permission scoping is global per role (no ownership-based access in MVP)
  • Seeded defaults: an Admin role (all permissions) and a Member role (basic read + create_lead), both editable
  • Status list ships empty — no seeded values. Admin must define at least one status before a lead can be created
  • New lead form rendered dynamically from current field definitions
  • Client list view with search by company name
  • Client detail page shell: header with system + custom fields, left rail with empty placeholders for engagements and recent artifacts
  • Edit client (in-place), delete client
  • Settings area with tabs: Profile, Team & roles, Fields, Workspace
  • Audit log: every create / edit / delete on clients, leads, users, roles, permissions, fields, statuses, and workspace settings is recorded with actor, action, target, before/after, and timestamp
  • Audit log viewer for users with the view_audit_log permission
  • Self-service profile updates (display name, password)
  • Admin-initiated password reset for forgotten passwords
  • Basic responsive layout — usable on tablet and mobile, optimised for desktop
  • UI in English only

Out of scope

  • Self-service password reset (forgot-password email flow)
  • Email verification on account creation
  • Two-factor authentication, OAuth, SSO, magic links
  • Multiple workspaces / multi-tenancy
  • Ownership-based permissions (e.g. "edit own clients only")
  • Custom fields on engagements, opportunities, or any other entity — only client/lead in this epic
  • Configurable kanban stages — those ship with the boards they belong to in EPIC-2 and EPIC-3
  • The Sales board itself (EPIC-2)
  • The Consulting board, engagement workspace, business flow, opportunities, report (EPIC-3)
  • Artifact upload, storage, list (EPIC-4)
  • Sales pipeline metrics, dashboards, reports
  • Bulk import / export of clients
  • Native mobile apps
  • UI translation into Uzbek / Russian / Cyrillic — those languages apply to client-facing reports only (EPIC-3)
  • Notifications (email, in-app, push)
  • Integrations with Telegram, email, or any external system

06User stories

Each story has acceptance criteria in Given / When / Then form. Every story must additionally satisfy the universal Definition of Done. Stories grouped by persona.

Team member
US-01Log in with email and passwordTeam member

As a team member with an account, I want to log in by entering my email and password, so that I can access HEAD's internal system.

Acceptance criteria
  • Given a valid email and password, when the user submits the login form, then they are authenticated and routed to the Clients page within 500 ms server-side.
  • Given an invalid email or password, then the user sees a generic error ("incorrect email or password") without revealing which of the two was wrong.
  • Given a deactivated account, then login fails with a generic error; the system does not disclose deactivated status.
  • Given successful login, then a session is created and persists for 30 days unless the user logs out explicitly.
  • No email verification step exists. No 2FA challenge exists. No "remember me" toggle exists — sessions are persistent by default.
US-02Log outTeam member

As a logged-in team member, I want to log out, so that my session ends and the next person on this device cannot use my account.

Acceptance criteria
  • Given a logged-in user, when they click Log out from the user menu, then the session is destroyed server-side and the browser is redirected to the login page.
  • Given a destroyed session, when the user presses Back or uses a stale URL, then they are redirected to login — the previous session cannot be resumed.
US-03See the app shell and navigateTeam member

As a logged-in team member, I want a consistent navigation shell on every page, so that I can find the Pipeline, the Clients list, Settings, and search without learning each page individually.

Acceptance criteria
  • Given a logged-in user, when any internal page is rendered, then a left sidebar shows Pipeline, Clients, and Settings in that order, with the current section highlighted.
  • Given the same shell, then a top bar shows a global search field, a "+ New lead" button, and a user menu (current user's name, Profile shortcut, Log out).
  • Given the current user lacks the create_lead permission, then the "+ New lead" button is hidden.
  • Given the current user lacks any settings-management permission, then the Settings sidebar item is still visible but only shows tabs they have access to (at minimum, their own Profile).
  • The Pipeline sidebar item lands the user on EPIC-2's Sales board once it ships; in EPIC-1, the Pipeline page renders an empty state explaining that boards are coming.
US-04View the list of all clientsTeam member

As a team member with the view_clients permission, I want to see a list of every client in the workspace, so that I can scan, sort, and filter the full book of business.

Acceptance criteria
  • Given the user has view_clients, when they open the Clients page, then a paginated table renders within 1 second for the first 100 clients.
  • Columns include the three system fields (company name, owner, status) plus any custom field marked as "show in list view" in Settings.
  • Each row links to the client detail page.
  • The list is sortable by any visible column (ascending / descending).
  • Filtering by status is available as a toolbar control above the table.
  • Given the user lacks view_clients, then the Clients sidebar item is hidden and direct URL access returns a permission-denied page.
US-05Search for a client by nameTeam member

As a team member, I want to type a company name into the global search and jump to that client, so that I don't have to scroll the Clients list every time.

Acceptance criteria
  • Given the user types at least 2 characters into global search, when they pause typing, then matching clients appear in a dropdown within 500 ms.
  • Search matches against the company name field with case-insensitive substring matching.
  • Each search result shows: company name, current status, owner.
  • Given the user selects a result, then they are navigated to that client's detail page.
  • Given the user lacks view_clients, then the search field is hidden.
  • Search results are scoped to clients the user is permitted to view (global permission in MVP — anyone with view_clients sees all).
US-06Create a new leadTeam member

As a team member with the create_lead permission, I want to capture a new lead in a single short form, so that the information lands in the system the moment a conversation happens instead of being lost in Telegram.

Acceptance criteria
  • Given the user clicks "+ New lead" in the top bar, when the form opens, then it renders the system fields (company name, owner, status) plus every custom field whose placement includes "new-lead form".
  • Company name is always required. Owner defaults to the current user and is editable. Status defaults to the first lead-eligible status (see definition below) and is editable. If no lead-eligible status exists, lead creation is blocked entirely with a banner directing admins to Settings → Workspace → Statuses.
  • Lead-eligible status — in EPIC-1's standalone phase (before EPIC-2 ships), this is any defined status. After EPIC-2 ships and introduces the board property, this narrows to "any status whose board property includes Sales." This is the canonical rule shared with EPIC-2 US-14; both stories reference the same gate.
  • Each custom field renders according to its type (text, dropdown, date, file, etc.) and respects its required/optional flag.
  • Given all required fields are filled, when the user submits, then the client record is created, the user lands on the new client's detail page, and an entry is written to the audit log.
  • Given a required field is empty, then submit is blocked with inline error messages and the form is not submitted.
  • Given the user lacks create_lead, then the "+ New lead" button is hidden and direct API calls return permission-denied.
  • The form does not require connecting the lead to an engagement at creation — engagements are added later (EPIC-3) or via the Sales board's Won transition (EPIC-2).
US-07Open and read a client detail pageTeam member

As a team member with view_clients, I want to open any client and see every captured field plus the placeholders for their engagements and artifacts, so that I have one place to read about that company.

Acceptance criteria
  • Given the user navigates to a client detail page, when it loads, then the header shows: company name, current status badge, owner, created date, and every custom field whose placement includes "detail page".
  • The left rail shows two sections: Engagements and Recent artifacts. In EPIC-1, both sections render empty-state placeholders with copy explaining that EPIC-3 and EPIC-4 populate them.
  • The right pane in EPIC-1 shows an empty-state explaining that engagement workspaces (consulting, implementation, training) will appear here once those modules ship.
  • System fields are visually distinct from custom fields in the header (different label style or section grouping).
  • The page never crashes if a field that was previously captured has since been deleted from the field definitions — old values are shown as read-only in a "Removed fields" section, retained for the audit trail.
US-08Edit a clientTeam member

As a team member with edit_client, I want to update any client's fields in-place, so that I keep the record accurate as I learn more.

Acceptance criteria
  • Given the user has edit_client, when they click a field on the detail page, then the field becomes editable with the appropriate input control for its type.
  • Given the user changes a value and confirms, then the new value is saved, the page reflects it immediately, and an audit log entry is written with before/after values.
  • Company name can be edited but never blanked.
  • Status can be changed to any status defined in the workspace.
  • Owner can be reassigned to any active team member.
  • Given the user lacks edit_client, then fields are read-only and edit affordances are hidden.
  • Edits respect each field's required/optional flag — a required field cannot be cleared.
US-09Delete a clientTeam member

As a team member with delete_client, I want to remove a client record that was created in error or no longer matters, so that the list stays meaningful.

Acceptance criteria
  • Given the user has delete_client, when they choose Delete from the client detail page, then a confirmation dialog appears requiring the user to type the company name to confirm.
  • Given confirmation is given, then the client is soft-deleted — removed from list and search results but preserved in the database, with a deletion record in the audit log including actor, target, timestamp, and a snapshot of the record at the moment of deletion.
  • Soft-deleted clients can be restored by anyone with manage_workspace via an admin tool (out of scope for this epic UI, but the data is recoverable).
  • Given the user lacks delete_client, then the Delete action is hidden and direct API calls return permission-denied.
  • Deleting a client does not delete any related engagement or artifact records (these will live in EPIC-3 and EPIC-4). The related records remain in the database in an "orphaned" state — preserved with the original foreign key intact but hidden from every UI surface that lists by active client. A dedicated admin UI to review or recover orphaned records is out of scope for MVP across EPIC-3 and EPIC-4; recovery, if needed, is a manual admin operation out of band.
US-10Update my own profileTeam member

As a team member, I want to update my display name and change my password from the Profile tab, so that my account reflects me and I can rotate my password without bothering an admin.

Acceptance criteria
  • Given the user opens Settings → Profile, then they see their display name (editable), their email (read-only), and a "Change password" affordance.
  • Given the user changes their display name and saves, then the change is persisted, reflected across the app, and audit-logged.
  • Given the user changes their password, when they submit the new password (entered twice), then it is saved as a hash, all other active sessions for this account are invalidated, and an audit log entry is written.
  • Email cannot be self-changed in MVP — admin-only.
  • Passwords must be at least 8 characters. No other complexity rules.
Admin
US-11Invite a new team memberAdmin

As an admin with manage_users, I want to create a new team account from Settings, so that a new hire or contractor can log in without going through engineering.

Acceptance criteria
  • Given the admin opens Settings → Team & roles → New user, then they see a form requiring email, display name, an initial password, and a role assignment.
  • Given the admin submits the form, then the account is created, the user can log in immediately with the provided credentials, and an audit log entry is written.
  • The initial password must be communicated to the new user out of band (e.g. Telegram, email outside the system) — the system itself does not send invitation emails in MVP.
  • The role assignment is required. The admin can pick any existing role (seeded or custom).
  • Email addresses must be unique across the workspace; duplicates are rejected at submit.
US-12Deactivate, reactivate, or delete a team memberAdmin

As an admin with manage_users, I want to stop a team member from logging in without erasing their history, so that records created by them remain intact while the account itself is suspended.

Acceptance criteria
  • Given the admin opens a team member's row in Settings → Team & roles, when they choose Deactivate, then the user's sessions are killed and future logins fail with the generic error message.
  • Deactivated users continue to appear as the "owner" on clients they previously owned. Their display name appears in italics or with a "deactivated" badge in lists.
  • Given a deactivated user is reactivated by the admin, then the user can log in again from the next attempt onward.
  • Hard deletion is intentionally not exposed in the UI in MVP — accounts are deactivated, not deleted, to preserve audit trail.
  • An admin cannot deactivate themselves. The system admin (hard-coded) cannot be deactivated by any admin.
  • Every deactivation, reactivation, and role change is audit-logged.
US-13Reset another user's passwordAdmin

As an admin with manage_users, I want to set a new password for a team member who forgot theirs, so that they can log back in — since there is no self-service forgot-password flow in MVP.

Acceptance criteria
  • Given the admin opens a team member's row, when they choose Reset password, then they enter a new password directly into a form.
  • Given the new password is set, then all of that user's existing sessions are invalidated, the password hash is updated, and an audit log entry is written.
  • The admin must communicate the new password to the user out of band.
  • The system admin's password cannot be reset from the UI by anyone — it is configured outside the database (see SEC-06).
US-14Create a custom roleAdmin

As an admin with manage_roles, I want to create a new role and pick which permissions it includes, so that I can model HEAD's team structure without engineering.

Acceptance criteria
  • Given the admin opens Settings → Team & roles → Roles → New role, then a form requests a role name and a multi-select of permissions from the full permission catalog.
  • Role names must be unique within the workspace.
  • Given the admin submits, then the role is created and can be assigned to team members from the user form.
  • The permission catalog presented to the admin is the union of all permissions registered by every shipped epic — in EPIC-1, this is the set listed in the glossary.
  • Every role creation and edit is audit-logged with the full before/after permission set.
US-15Edit, rename, or delete a roleAdmin

As an admin with manage_roles, I want to change a role's name or its permissions later, and to remove roles no longer in use, so that the role catalogue evolves with the team.

Acceptance criteria
  • Given the admin edits a role's name, then the change propagates to every team member assigned to that role immediately, no logout required.
  • Given the admin adds or removes permissions on a role, then every team member with that role gains or loses access on their next request (no session-cached permissions).
  • Given the admin attempts to delete a role currently assigned to one or more users, then the system blocks the deletion until those users are reassigned to a different role.
  • The seeded Admin role and Member role can be renamed and re-permissioned. The Admin role cannot be deleted (it is the seeded fallback for the workspace).
  • Every change is audit-logged.
US-16Assign or change a team member's roleAdmin

As an admin with manage_users, I want to change which role a team member holds, so that their permissions follow their actual responsibility.

Acceptance criteria
  • Given the admin selects a role from the user's row, when they confirm the change, then the new role takes effect on the user's next request.
  • Each team member holds exactly one role at a time in MVP (no multi-role).
  • Removing the last admin user is allowed only because the hard-coded system admin always remains.
  • Every role assignment change is audit-logged.
US-17Create a custom field on client / leadAdmin

As an admin with manage_fields, I want to add a new field to the client/lead record from Settings, so that HEAD captures exactly what HEAD wants — without engineering.

Acceptance criteria
  • Given the admin opens Settings → Fields → New field, then a form requests: field name, field type, required/optional, default value (where applicable), help text, display order, dropdown options (where applicable), and placement.
  • Supported field types: single-line text, long text, number, date, single-select dropdown, multi-select dropdown, checkbox, file upload.
  • Placement is a multi-select with these options: show on new-lead form, show on client detail page, show in clients list view. A field can be in any combination of the three, or none of them (defined but not surfaced).
  • Field names must be unique across client/lead fields. Internal field identifiers are derived from the name and immutable once created.
  • Given the admin submits a valid form, then the field is created and appears immediately in every place its placement specifies, with no deploy.
  • A field marked required cannot be required retroactively without admin acknowledgement that existing records with empty values will be flagged (not blocked).
  • Every field creation is audit-logged with the full configuration.
US-18Edit, reorder, or delete a custom fieldAdmin

As an admin with manage_fields, I want to refine a field after creation, reorder fields in the form, and remove fields that don't matter anymore, so that the schema adapts as the team learns what to capture.

Acceptance criteria
  • Given the admin edits a field's name, help text, default, options, placement, required flag, or display order, when they save, then the change is reflected everywhere the field appears within seconds. Existing data is preserved.
  • Field type cannot be changed after creation (type changes risk data loss). To change a type, the admin must delete and recreate.
  • Removing a dropdown option does not delete records that hold that value — those values are shown as read-only and flagged "removed option" in the UI.
  • Given the admin deletes a field, when they confirm, then the field disappears from all forms and detail pages. Existing data is preserved in a "Removed fields" section on the affected records (visible only to users with view_clients) and retained in the audit log.
  • System fields (company name, owner, status) cannot be deleted, cannot have their type changed, and cannot be marked optional. They can be renamed for display.
  • Every field edit, reorder, and delete is audit-logged.
US-19Configure the status listAdmin

As an admin with manage_workspace, I want to define the list of statuses a client/lead can hold, so that HEAD's vocabulary for "where is this account?" matches how the team actually talks.

Acceptance criteria
  • Given the admin opens Settings → Workspace → Statuses on a fresh installation, then they see an empty list with a clear empty-state message: "Define your first status before the team can create leads."
  • The admin can add a status, rename a status, reorder statuses, and remove a status.
  • Each status carries: label (display string), display order. EPIC-2 will extend this entity with a "board" property and a "type" property; EPIC-1 just defines the bare status record.
  • Given the admin removes a status currently held by one or more clients, then deletion is blocked with a list of affected clients; the admin must first reassign those clients to another status.
  • The first lead-eligible status in the ordered list is the default for new leads. If no lead-eligible status exists, the "+ New lead" button is disabled with a tooltip explaining the admin must configure statuses first. (See US-06 for the definition of lead-eligible — it evolves when EPIC-2 introduces the board property.)
  • Every change is audit-logged.
  • Status configuration applies workspace-wide, not per-engagement-type. (Engagement-level workflow states live with their respective boards in EPIC-2 and EPIC-3.)
US-20Review the audit logAdmin

As an admin with view_audit_log, I want to see a chronological log of every change made in the system, so that I can answer "who changed what, when?" without engineering.

Acceptance criteria
  • Given the admin opens Settings → Workspace → Audit log, then they see a paginated, time-descending list of every mutating action.
  • Each entry records: timestamp, actor (user display name + email), action (create, edit, delete, login, logout, password change, role assignment, etc.), target entity (client, user, role, field, status, workspace setting), and a structured before / after payload where applicable.
  • The log is filterable by actor, target type, target id, and date range.
  • Audit log entries are immutable — there is no Edit and no Delete on entries from any UI or API.
  • Login and logout events are recorded.
  • Failed login attempts are recorded with the email tried (regardless of whether the account exists), the source IP if available, and the timestamp.
  • Audit log retention is at least 12 months.
US-21Update workspace settingsAdmin

As an admin with manage_workspace, I want to update the workspace's display name and basic preferences, so that the system reflects HEAD branding accurately.

Acceptance criteria
  • Given the admin opens Settings → Workspace → General, then they can edit: workspace display name, default time zone, default currency.
  • The workspace name appears in the browser title and at the top of the sidebar.
  • Every change is audit-logged.
  • Workspace settings apply to the single workspace this installation hosts — multi-tenant is out of scope.

US-24System admin cannot be deleted, deactivated, or demoted from the UISystem admin

As the founder, I want the system admin account to be immune to any in-product action that could lock it out, so that a misconfiguration cannot remove the only path back into the system.

  • The system admin can change their own display name from Profile, but cannot delete their own account.
  • The system admin's email is configured in the deployment and surfaced as read-only in Profile.

07Definition of Done

Applies to every user story. A story is not done until every item below is true.

  • All acceptance criteria pass the automated test suite (unit + integration + end-to-end).
  • Every mutating path writes an audit log entry that survives a process restart and database backup.
  • Every permission-gated UI affordance is hidden when the user lacks the permission, and every permission-gated API endpoint returns permission-denied when the user lacks the permission. Both checks tested.
  • The page is usable on a 1280px desktop viewport without horizontal scroll, and degrades to a single-column readable layout on 375px mobile width.
  • The change is documented in the admin guide if it affects admin behaviour, and in the team-member guide if it affects regular-user behaviour.
  • Strings are English. No emoji, no AI-washing language (e.g. "fully autonomous", "magic"), no ALL CAPS, sentence case throughout.
  • HEAD product lead (Abdulbosit) has signed off.

08Security & data protection

The foundation is the gate to every other module. A weakness here is a weakness everywhere. The rules below are non-negotiable and apply alongside every user story.

SEC-01Passwords stored as hashes onlySecurity
Required behaviour
  • Given a user creates or changes a password, when the password is persisted, then only a salted, slow-hashed digest (Argon2id or bcrypt at a current-recommended work factor) is stored. The plaintext is never written to any database, log, or queue.
  • Given the system admin's password is rotated, then it is rotated in the deployment configuration; the application reads it from the configured secret store, never from the user database.
  • Password hashes are never returned by any API.
SEC-02Session integritySecurity
Required behaviour
  • Sessions use a cryptographically random, opaque token, stored server-side and identified by a cookie or token header. The cookie is set with HttpOnly, Secure, and SameSite=Lax.
  • Given a user logs out, deactivates, changes their password, or has their password reset by an admin, then every existing session for that user is invalidated server-side within seconds.
  • Session lifetime is 30 days of inactivity (sliding) with a hard cap of 90 days regardless of activity.
  • The session token never contains permission information — permission is re-evaluated on every request against the current role and the current permission set.
SEC-03Permission enforcement on every mutating actionSecurity
Required behaviour
  • Given any API endpoint that creates, edits, or deletes data, when a request arrives, then the server checks the actor's current role and the permissions on that role before executing any database write.
  • Permission checks are server-side, never client-side. Client-side hiding of UI is a UX concern, not a security one — the server is the source of truth.
  • An endpoint that has not registered a permission requirement is denied by default (deny-by-default policy).
  • Permission registrations are part of code review and appear in the permission catalog visible to admins.
SEC-04Failed login throttlingSecurity
Required behaviour
  • Given five consecutive failed login attempts on a single email within 15 minutes, then further attempts on that email are throttled with exponential backoff for the next 15 minutes.
  • Given twenty failed login attempts from a single IP within 5 minutes across any emails, then further attempts from that IP are throttled for 15 minutes.
  • Throttle messages do not reveal whether an email exists in the system.
  • Every failed login attempt is recorded in the audit log (US-20) with the email tried and the source IP if available.
SEC-05Audit log integritySecurity
Required behaviour
  • Audit log entries are append-only. No application code path exists to update or delete an entry. Database-level constraints enforce this where possible.
  • Audit log entries cannot be edited by the system admin from the UI.
  • Audit log access requires the view_audit_log permission and is itself logged ("user X viewed the audit log").
  • Audit log backups are part of the standard database backup, retained for at least 12 months.
SEC-06Hard-coded system admin protectionSecurity
Required behaviour
  • System admin credentials are stored in the deployment configuration (environment variable or secret manager), not in the user database. The application reads them at boot.
  • No UI flow can delete, deactivate, demote, or reset the password of a system admin account.
  • A system admin's role assignment in the database, if any, is ignored — the "system admin" status is determined by matching the configured email at request time.
  • The number of system admin accounts is configured externally and is typically 1 or 2 (the founders).
SEC-07Workspace isolationSecurity
Required behaviour
  • Every database query for clients, leads, users, roles, fields, statuses, and audit log entries is scoped to the current workspace identifier.
  • Even though MVP ships a single workspace, the schema and query layer assume multi-tenancy from day one so future installations cannot be retrofitted into leaks.
  • No API endpoint accepts a workspace identifier from the client — it is always resolved from the authenticated session.
SEC-08Input validation and output encodingSecurity
Required behaviour
  • All user input is validated server-side against the declared field type before persistence. Type mismatches are rejected.
  • All user-provided text rendered in HTML is escaped to prevent cross-site scripting. Markdown is rendered through a hardened library with a strict allowlist.
  • File uploads accept only an admin-configured allowlist of MIME types and are stored outside the web root.
  • Database access uses parameterised queries exclusively — no string-concatenated SQL.

09Glossary

Admin
A team member whose assigned role includes the management permissions (manage_users, manage_roles, manage_fields, manage_workspace, view_audit_log). The seeded "Admin" role has all of these.
Audit log
An append-only ledger of every mutating action in the system: who, what, when, before / after.
Client
A company HEAD does business with. The same record as a Lead — distinguished only by the status field.
Custom field
An admin-defined field on the client/lead record. Has a name, type, optional default, help text, required flag, display order, and placement.
Custom file field vs. artifact
A custom field of type "file upload" (this epic) is a structured slot on the client record — one specific file (e.g. a signed contract) tied to one named field, validated by the admin's field config. An artifact (EPIC-4) is an unstructured upload attached to a client (or engagement) with no field semantics — site visit photos, voice memos, chat exports, anything. When in doubt: if the file represents one of a known set ("contract," "NDA"), use a custom file field. If it's part of a growing pile of raw material, use an artifact.
Field placement
A multi-select on each custom field controlling whether the field appears on the new-lead form, on the client detail page, in the clients list view, or any combination — including none.
Hard-coded admin / System admin
An account seeded at installation from deployment configuration. Has implicit all-permissions, cannot be deleted, deactivated, demoted, or password-reset from the UI.
Lead
A client at an early status (typically the seeded "Lead" or "In communication" status). Same database record as a Client.
Member
The seeded default role, granted basic read and create-lead permissions. Fully editable by an admin.
Permission
A discrete, named capability — e.g. create_lead, edit_client, delete_client, manage_users, manage_roles, manage_fields, manage_workspace, view_clients, view_audit_log. Future epics register additional permissions; the catalog grows over time.
Permission catalog
The union of every permission registered by every shipped epic. Visible to admins in Settings → Team & roles. Surfaces only registered permissions, not arbitrary strings.
Role
A named bundle of permissions. Created and managed by admins. Each team member holds exactly one role.
Session
A server-side authenticated context for one logged-in user. Identified by an opaque token. Invalidated on logout, password change, password reset by admin, or deactivation.
Status
The current lifecycle stage of a client/lead. Comes from an admin-defined ordered list. The list ships empty — admins define the team's vocabulary before any lead can be created. EPIC-2 extends the status entity with board and type properties.
System field
A field the system itself owns and the admin cannot delete: company name, owner, status.
Team member
Anyone with an account in the workspace. Permissions follow the assigned role.
Workspace
The container for everything in one installation. MVP ships a single workspace; the data model assumes multi-tenancy for future portability.
